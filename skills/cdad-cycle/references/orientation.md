# Orientation — operating the CDAD CLI with bounded context

`<skill-dir>` is the directory of the loaded `cdad-cycle` skill. This reference is
short on purpose: it orients the orchestrator to the **compact view** and to the
**frequent operations** without rebuilding the CLI from its code, and it fixes the
**evidence-capture pattern** so the real return of the CLI is never masked.

> Scope note (005-003 T1): this is the operating skeleton. The **executable
> examples asset** (`<skill-dir>/assets/orientation-examples.json`, located by its
> declared path, never by prose) and the multi-session summary rule (R4) are
> delivered by **T2/T3**; this reference **cites** the asset and does not duplicate
> the examples.

## 1. The compact view first (read-only)

The first orientation action is the compact operational view of
`<skill-dir>/scripts/cdad_packet.py`:
a **single JSON document** on stdout, generated by code from the existing sources
(`docs/.cdad-state.json` operational fields, the active execution context, the
active packet, `docs/cdad-policy.json`, the installed version check). It does
**not** emit `stage_history`, it is **read-only** (the state stays byte-identical)
and it is bounded by a normative byte limit (default 16.384 B).

```sh
python3 "<skill-dir>/scripts/cdad_packet.py" status --project-root ROOT
```

- `entry` selects the next action explicitly: `continuity-reconcile` (a pending
  `prepared`/`dispatched` packet, or an active execution), `next-unit` (resting
  with no pending work) or `diagnosis` (incomplete configuration). It is a map,
  **not** an inference by `current_stage` or by the word "inicializar".
- `next` names the route **and its declared source**; with a `prepared` packet
  the route names the **natural action — dispatch it** (validate → `begin` →
  `--record-dispatch`), with `--replace-packet` only as the **conditional
  branch** (a changed contract, `project-execution.md` §164-182); `unknowns[]`
  names the causes of what could not be projected (**never** a fabricated `0`).
- Above the limit the view **fails closed** (rc≠0) with no partial projection and
  a diagnostic that names the limit and `--max-bytes N`.

Ownership: this section owns only the "view first" rule. The orchestrator agent's
directive section carries the full context discipline; the rotation rule — rotate
the session at task boundaries, not mid-unit — is cited from there, not restated
here.

## 2. Evidence capture — never mask the real `rc` (spec §2.5)

Reading the return code through a pipe (`| head`, `| tail`) replaces it with the
last command's code. Capture the **CLI's own** `rc`:

```sh
# WRONG: $? is head/tail's rc, not the CLI's
python3 "<skill-dir>/scripts/cdad_packet.py" status --project-root ROOT | head

# RIGHT (bash): PIPESTATUS[0] is the CLI's rc
python3 "<skill-dir>/scripts/cdad_packet.py" status --project-root ROOT | head
rc=${PIPESTATUS[0]}

# RIGHT (portable): no pipe; bound the output separately
out=$(python3 "<skill-dir>/scripts/cdad_packet.py" status --project-root ROOT); rc=$?
```

`set -o pipefail` is an alternative where it is available. The bounded output goes
to the context; the **complete** evidence stays available **by reference**.

### Project root resolution

Every CLI resolves its **own** `--project-root` the same way: against the
current working directory and requiring an existing directory, so a relative
root such as `.` is accepted. The rule is stated once in
`project-execution.md` §1; the former root-relative asymmetry between
`cdad_packet.py` and `cdad_continuity.py` — and the `status` view's diagnosis of
it — is gone.

### Dispatch-attempt input (`docs/attempt.json`)

The record-of-dispatch input declares the exact fields `runtime`,
`model_configured`, `model_reported`, `session`, `started_at` plus `provenance`
(see `project-execution.md`). A minimal valid example and a negative case (an
`attempt.json` without `runtime`) are part of the executable asset delivered by
T2: the invalid input **fails closed naming the missing field**, and the asset
declares that expectation.

### Continuity update (`UPDATE.json`)

`begin`/`checkpoint` freeze the write-ahead checkpoint from an `--update`
document: the idempotency key `(execution_id, packet_id, attempt)` plus the D11
content `goal` / `decisions` / `uncertainties` / `next_action` (and an optional
`budget` snapshot). A malformed update fails closed naming the violated field
(the CLI never persists a schema-invalid head).

### Executable examples asset

The minimal valid inputs and the invocations above live in the canonical asset
`<skill-dir>/assets/orientation-examples.json` (an `examples[]` array with
`id`/`kind`/`target` and the `input`/`command`), including the compact-view
invocation and the `open-unit` unit-open invocation. This reference **cites** the
asset; it does not duplicate the examples.

## 4. Version disposition and the meter (spec §2.4)

Reuse the **installed** `cdad-version-check.py` (not the checkout copy, which
reports `UNKNOWN`). It prints exactly one verdict, each with its own rc; only
`COHERENT` is "ok":

| Verdict | rc | Meaning |
|---|---|---|
| `COHERENT` | 0 | project, agents and CLI share the same version |
| `DRIFT` | 1 | **incoherencia**: the three are NOT the same version |
| `NO-PROJECT-AGENTS` | 4 | nothing loaded yet to compare (version NOT verified) |
| `UNKNOWN` | 3 | an installation marker is missing (version NOT verified) |

`UNKNOWN` and `NO-PROJECT-AGENTS` are **ausencia**: the version is **not
verified**. `DRIFT` is **incoherencia**: a real divergence, distinct from
absence. Any rc ≠ 0 reads as "not verified as coherent", never as ok.

The view's `version` block reports that distinction (an **additive** extension
of 005-003 §2.4: `verdict`/`verified`/`cause` are conserved). Ante un `DRIFT`
the block **names the leg that diverges** (`project` / `agents` / `CLI` /
`claude-code`), **read** from the check's own lines — never inferred — and,
**only** when that leg is `project`, **what resolves it**: the next `prepare`
republishes the project's derived agents (`project-execution.md` §143-146).
Another leg gets **no** promise; absence carries **no** resolution clause.

**The absent meter.** The 005-002 meter may be **absent** from the installed
skills (the "medidor no instalado" case). That is declared **ausencia** (version
not verified), **distinta** de `DRIFT`, which is **incoherencia** — an absent
meter is **never** `DRIFT`. While the meter is not installed, measure with the
repository artifact **read-only**; deploying it is the owner's and out of scope.

Republicar by the legitimate path (`prepare` and its derivatives) and verify
afterwards; do not duplicate manifest/marker inspections without a new
contradiction. Declared limit: matching files does **not** prove what an open
session loaded.

## 5. Actionable errors — no shortcuts (spec §2.5)

Errors use the `ERROR: …` format and name the **cause** and the **recovery
path**. Recovery is legitimate only within the contract:

- **no** ampliar alcances to continue (never widen a scope to move on);
- **no** fabricar aprobaciones (never invent authority or an approval);
- **no** borrar registros (never delete records or evidence).

A blocked step is declared, not patched over: the actionable error names what is
missing and how to continue, and the block is reported to the orchestrator.

## 6. Operation → executable owner (single documented map)

The compact view also projects `situation` and `next.operation`
(`verb`/`script`/`procedure`/`source`). This section is the **single owner** of
the verb → script map; the orchestrator and the derived agents **cite** it and
never copy the table. `script` and `procedure` are relative to the installed
`<skill-dir>`.

| Verb | Executable owner |
|---|---|
| `status` | `scripts/cdad_packet.py` |
| `validate-packet` | `scripts/cdad_packet.py` |
| `open-unit` | `scripts/cdad_packet.py` |
| `prepare` | `scripts/cdad_packet.py` |
| `render` | `scripts/cdad_packet.py` |
| `prepare --record-dispatch` | `scripts/cdad_packet.py` |
| `begin` | `scripts/cdad_continuity.py` |
| `checkpoint` | `scripts/cdad_continuity.py` |
| `reconcile` | `scripts/cdad_continuity.py` |
| `resume` | `scripts/cdad_continuity.py` |
| `trigger` | `scripts/cdad_continuity.py` |
| `receive` | `scripts/cdad_result.py` |

`prepare --record-dispatch` registers the dispatch of an already prepared
packet; it is **not** the `record` verb of the transport entry (native/external
transport keeps its own reference and is never a fictional subcommand of
`cdad_packet.py`). `diagnose` is an operator indication of `next.operation`, not
a subcommand: it carries no script.

`next.operation` is the **first verifiable step**, never a macro. For a prepared
packet it says `validate-packet`; the procedure then continues with the
protocol above (validate → `begin` → transport → register).
